## `bun run test:strict` (#175) — full mechanics

**`bun run test:strict` (#175) is how a review gets an opposable verdict from a noisy suite.** The systematic failing population is machine-dependent (PATH corruption left by earlier files, `mock.module` leakage, live endpoints, real defects) — its live count lives in each machine's gitignored `.test-strict-baseline.json`, never in this file (a derived count here has drifted on every capture since). The strict runner executes the suite **bounded and scoped to `packages/cli/src`** (`--timeout 15000` per test + a 420 s wall-clock kill, because bun's timeout covers tests, not hooks — an unbounded run looped >35 min on 2026-09-29; a bare `bun test` also executes any compiled `dist/`, whose fixture-resolution failures are build artifacts, not a test population — measured 2026-10-01: 9 → 52 fails with zero source changes), parses the failing population keyed `file > describe > test` (two files hosting the same describe path are two entries — a name-only key collapses them and hides a new red behind a same-named baseline entry), synthesizes a named entry per module-load death (`# Unhandled error` block → `file: load error #N`; bun 1.3.13 **and** 1.3.14 double-count one such death into BOTH its `fail` and `error` summary counters, so accounting is `entries === max(fail, error)`), and **refuses a verdict** (exit 3) whenever the parsed entries cannot account for bun's own counters or the `Ran N tests across M files` line is absent (truncated output) — a parser blind to a failure shape is how a file dying at import turns into a false green. Comparison against the baseline is by **reproduction, never by count**: fresh entries trigger exactly one confirmation re-run, and only names present in BOTH runs are regressions (exit 1) — a deterministic new red cannot hide behind flaky slots, and a fail that does not reproduce is noise whatever its count. Baseline fails that vanish are reported as improvement; ENV-GATE manifests are consolidated into one end-of-run block. First use on a machine: `bun run test:strict -- --learn`, then re-run to compare. **A learned baseline is a snapshot, not an instrument — re-learn it after any land that removes a cause of load-time death.** **The 420 s wall is overridable per seat** (`CLAUDISH_STRICT_WALL_CLOCK_MS`, positive integer of ms up to `2147483647` — above that `spawnSync`'s timeout misbehaves (measured: 2^31 kills at once and reads as a flaky tail), so the resolver refuses it on the same warning path; default unchanged; invalid values fall back to the default with a warning — never a silent bound change). Arbitrated 2026-11-15 (#641 C3) after the v14 population was measured not to fit 420 s on the seats that run it (po-2024 and po-2028 both killed ETIMEDOUT while main's baseline fits — population and/or seat load, not a port defect; sharding was considered and rejected). The kill line names the wall that fired. ⚠ **Commensurability is per workflow, not per repo**: `release.yml` installs `bun-version: latest`, while the fork's test workflow (`.github/workflows/test.yml`, #570) deliberately pins **1.4.0**. Seats measured 2026-10-21: ai-01 1.3.13, po-2024 1.3.14; 1.4.2/1.4.3 reported on others. A seat on a different bun from the CI run it compares against is not commensurable — a bun-only defect is green in one and red in the other (measurements: #391). Classes 2/2b (stale contract, win32 defect — TEST-15) stay red and stay in the baseline by design; a static pin in `env-gate.test.ts` refuses ever gating them.

## Partitioned mode (`--partition`) — when the population does not fit one process (#641 C3)

The v14 population dies as a single `bun test` process long before completion: crash zone measured at ~176 files / ~1.3 GB RSS, and no directory-shaped slice is a bound (src root 151 files, `providers` 131, `handlers` 119 — three "partitions" sit at 68-86 % of the crash point). **`--partition` / `--partition=N`** (default N = 50) slices the SORTED test-file list into consecutive blocks of at most N files — bounded by COUNT, never by directory, so no slice can exceed N however any directory is populated — and runs each partition as its own `bun test` process (exact `./path` args; a bare path arg is a regex filter in bun, not a file selector). The per-seat wall clock applies PER PARTITION.

Measured on po-2024 (pre-merge head `bc8bf2b3`, #1114): 660 files → 14 partitions, **19 min 07 s** wall, slowest partition P12 = **409 s** (11 s under the DEFAULT 420 s wall — the default is not a safe bound at N = 50 on that seat; the run set `CLAUDISH_STRICT_WALL_CLOCK_MS=1800000`), peak RSS **~592 MB** per process vs ~1.3 GB at the single-process death.

Verdict discipline carries over, per partition:

- **A crashed or unaccountable partition refuses the verdict (exit 3)** — its keys are unknown, never "zero fails"; the refusal names the partition and its FULL file list.
- Observed = UNION of the partitions' entries; the confirmation re-run visits only the partitions hosting fresh entries; an entry whose file maps to no partition is refused as a foreign population (review #1114, third review).
- **A reproduced entry whose FILE passes when run ALONE is labeled `CONTEXT-SENSITIVE`, not `NEW FAILING` (#641 C4).** Reproduction on a partition is not proof that the test is at fault: REQ-9 of `code-mode/sandbox/script-runtime.test.ts` reproduced on its partition and passed alone on ai-01 (41/41). After the confirmation pass, each file hosting a reproduced entry is re-run ONCE alone (one run per distinct file, bounded by the same wall clock). Entries absent from that alone-run are context-sensitive — the surrounding population (PATH corruption, mock leakage, leftover state) is the suspect, not the test — and leave the `NEW FAILING` count and list; entries still failing alone stay NEW FAILING. **Exit stays 1 either way**: a label is not a green. An alone-run that cannot be read (kill, unaccountable counters, population gap, foreign entry) excuses nothing — its entries stay NEW FAILING and a `⚠ alone-run … could not be read` line says so. Single-process `main` (no `--partition`) is unchanged: it has no per-file delivery to re-run.

- **Learn records a partition manifest (N + boundaries) in the baseline**; a verify at a different N — or against a single-process baseline — refuses BEFORE any partition is burned (fail fast). Boundary drift alone is a warning: entries still compare by name.

**Exit-3 refusal modes — all of them, single-process and partitioned alike** (a verdict is only as good as the accounting behind it; exit 3 is a deliverable, the printed reason is the finding, never a prompt to relaunch):

- **Unaccountable counters**: the parsed entries cannot account for bun's own `fail`/`error` summary counters — a parser blind to a failure shape is how a file dying at import turns into a false green.
- **Over-counting population echo**: bun's `across M files` M exceeds BOTH the delivered entries and the files fed in — the union does not hold (multi-file state leakage inflates what one process saw; ±1 is a zero-test file, a persistent gap means the accounting is broken).
- **Foreign population**: an entry names a file outside the delivered population — refused in EVERY mode, `--learn` included; learning another population's name is how a baseline starts lying.

**`--learn` first is an obligation, not advice**: a partitioned verify against an absent or single-process baseline refuses on the manifest check above, so the first act on a seat is `bun run test:strict -- --learn --partition`. A learned baseline is still a snapshot — re-learn after any land that removes a cause of load-time death.

The default stays single-process until the mode is measured on **two seats** (arbitration c.6953832192): po-2024 measured (above); the second seat is the open half of grain C4.

## bun test traps — an in-process `Bun.serve` mock dies after a `node:http` server has lived in the process (#593, #604)

**Never mock HTTP through `Bun.serve` in a test file that can run after a proxy route test.** Measured 2026-10-23 on win32 bun 1.3.14 **and** ubuntu-24.04 bun 1.4.0, from a 30-line standalone repro plus a two-file in-suite repro:

- Once **any `node:http` server** has lived in the `bun test` process, **every `Bun.serve` created afterwards is unreachable** (fetch answers Bun's welcome page). The real proxy listens through `@hono/node-server`, so each `proxy-server-*.test.ts` route test is a poison source; a *live* hono server poisons too, a closed one heals nothing.
- The poisoned fetch does not fail — it succeeds with Bun's default page: `200 text/plain` `"Welcome to Bun! To get started, return a Response object."`. A JSON parser downstream reports `SyntaxError: Failed to parse JSON`, which is what the CI signature looked like for three weeks. A `node:http` client **hangs**, a raw `net.Socket` connection **hangs**.
- Irrelevant to the outcome: hostname (`127.0.0.1` / `localhost` / `0.0.0.0`), fixed vs ephemeral port, `server.stop()`, `closeAllConnections()` + `close()`, shutdown order, and whether the mock or the hono server came first in the *same* file. A single file run alone is green — no `node:http` server has lived in that process yet, which is exactly why this class never reproduced in isolation.
- **The fix is not a workaround for a Bun bug to be re-tested each release**: stop depending on in-process dispatch. `packages/cli/src/test-support/stub-fetch.ts` exports `installStubFetch(handler)` / `hangUntilAborted(req)`, which answer the same wire semantics as a server (status, headers, JSON/SSE bodies, abort on the client's own `AbortSignal.timeout`) with no socket. Files migrated by #604: `handlers/shared/mcp-searxng-client.test.ts`, `handlers/shared/web-search-executor.test.ts`. The pin in the former (`the mock transport is a fetch stub, not a Bun.serve`) fails loudly if someone reinstates a serve-based mock there.
- A **standalone script** (`bun run path/to/file.ts`, e.g. `fork/server/relay-e2e.ts`) is its own process and is **not** exposed — the poison needs a `node:http` server in the *same* process. `node:http` mocks (`fork/server/relay-keyless-forward.test.ts`) are the safe class too: they are reachable, and they are not victims of the trap.

Second bun trap, encoded in the same helper: **awaiting an `AbortSignal.timeout(n)` abort inside `bun test` hangs forever when that timer is the only pending wakeup**, and a handler promise that never settles suspends the runner at exit. `installStubFetch` keeps a `setInterval(…, 5ms)` alive for the duration of the guarded promise, and `hangUntilAborted` rejects off the request's own abort event instead of returning a forever-pending promise.

Third bun trap (#272 race, measured 2026-10-24, ~1 h lost): **a SEPARATE test file importing a module that another test file replaces via `mock.module` does not fail — it HANGS.** `mock.module` is process-global with no unregister; `openrouter.test.ts` replaces `../all-models-cache.js`, and a sibling file statically importing the same module binds to the mock and never completes (`rc=124`, per-test `--timeout` never fires, 0 bytes of output — the capture is the tell). The fix is placement, not wiring: the pins live in the EXISTING file that owns the `mock.module`. Order-dependent corollary: with both files in one process and `openrouter.test.ts` first, the race turns red already on `main`; in alphabetical order it does not fire — so it can pass on one seat and hang on another.

Same trap, load-death flavor (#794, measured 2026-10-31): under bun **1.4.0** the process-global replacement binds every LATER static import in the same process even when nothing hangs — a factory that omits an export strands the next importer at link time. `team-cli.test.ts` mocked `./team-grid.js` with only `runWithGrid`, and `team-grid-failure-details.test.ts` (alphabetically later, landed #584) died with `SyntaxError: Export named 'buildTeamStatus' not found` — the fork CI's only red, invisible in the job conclusion because the workflow pipes `bun test | tee`. 1.3.14 seats stayed green (no cross-file propagation), the per-workflow commensurability caveat above. The fix: the factory spreads the real module (`import * as real; ...({ ...real, overridden })`), so sibling exports stay live for every later importer.

## CI reading rules — executions vs copies, and the pinned biome verdict

**A job copied by "re-run failed jobs" is not an execution.** GitHub's re-run copies the GREEN jobs of the previous attempt into the new run with an identical `started_at` (only the failed jobs actually re-execute). Any acceptance criterion of the form "3 real green executions of shard X" must count DISTINCT `started_at` values per job name, never attempt numbers: three attempts of one run can be ONE real execution plus two copies. Codified by ai-01 in the #984 flake AC (measured on run 42937909451, where attempts 2 and 3 of the same macOS job shared the copied green siblings). `gh api repos/<r>/actions/runs/<id>/jobs?per_page=100 -q '.jobs[] | .name + " " + .started_at'` is the instrument; `gh pr checks` shows only the latest attempt and cannot see the copy.

**The `typecheck · lint` job — the `static` job of the `replatform/v14` workflow, the only place lint runs today (main's `test.yml` has no lint job) — runs the REPO-PINNED biome, and a global `npx biome` is not commensurable.** Measured 11/11 (PRs #989/#991, both targeting `replatform/v14`): a global `npx biome check .` reported exit 0 while the CI job was red with 6 errors (organizeImports + format) in the PR's own files. The CI job installs with `bun install --frozen-lockfile` and runs `bun run lint` → `biome check .` from `packages/cli`; the global npx resolved a different biome version whose organizeImports/formatter verdicts differ. The local command that makes faith: `packages/cli/node_modules/.bin/biome check . --diagnostic-level=error` from `packages/cli` (the scoped directory matters too — root-level JSON files carry pre-existing format errors that are out of the job's scope). `biome check --write <files>` with the same pinned binary is the fix; error-level output isolates the real errors from the ~1 649 pre-existing warnings (`noExplicitAny`, `noExcessiveCognitiveComplexity`) that saturate the default `--max-diagnostics=50` display and hide them.

**A hermetic · macOS flake family is rerun, not fixed in the PR's diff** (#984): same SHA green and red across runs means the shard moved, not the code. Read the failing test's NAME before touching anything — a picker paint-order flake is a test-only fix on its own PR, never a drive-by in an unrelated one.

## CI gating — "exit 0 + zero errors" does not prove a check ran (#981)

A green CI step is only as honest as the command it ran. **A command that exits 0 having done nothing reads exactly like a command that passed.** Measured 2026-11-11 (#981): the root `bun run typecheck`'s bridge half was `bun --cwd packages/macos-bridge run typecheck` — on bun ≥ 1.3 that form prints a usage dump and exits 0 without running anything, so every seat's typecheck covered `packages/cli` only while the summary implied both. The bridge, when actually executed (`bun run --cwd packages/macos-bridge typecheck`), was red (TS6306 + 28 real type errors the dead check had been hiding). Consequences:

- **Verify the check ran, not just its exit code**: the instrument must show the sub-command's own output (here, two `tsc --noEmit` passes), not a usage dump. A `grep -c 'error TS'`-style counter reads 0 both for "clean" and for "never executed" — count the *expected* evidence lines, not just the absence of error lines.
- **The fix is a measured red/green cycle on the target that was silently skipped**, not on the wrapper: prove the previously-dead half goes red on the unfixed tree and green after, so the gate demonstrably gates the new surface.
- Same family: a workflow that pipes `bun test | tee` hides a per-file load death behind the job's `success` conclusion badge (see the #794 trap above) — read the fail counter in the job log, never the badge.
